# Release Gopher

Work in `mbuvarp/gopher`. Read [release setup and recovery](../../../docs/updates.md#manual-github-releases) and the current release workflow before starting. Reuse `scripts/release.py` and `scripts/bundle.py` for validation; do not invent another publisher or update-signing process.

For a request only to validate an already-prepared commit, skip version/changelog
editing and use validation mode for that eligible commit. For preparation-only work,
stop at the requested artifacts; do not infer permission to commit/push or publish
unless the request includes those actions. The complete flow below applies to a
request to prepare and publish a release.

## Establish the release scope

- Fetch `origin/main` and inspect the working tree. Base release preparation on fresh main, using a clean temporary worktree if needed to preserve other work. Do not carry unmerged feature commits or unrelated working changes into a release.
- Fetch all GitHub releases with pagination. Consider published stable `v<major.minor.patch>` releases and compare versions numerically, using the highest version as the baseline. API/authentication failures are blockers, not evidence of a first release. Verify the baseline tag locally before reviewing its changes through the selected main commit.
- Review the changes, Cargo.toml/Cargo.lock, and existing changelog. Note the exact main commit being reviewed. Check branch rules: the user's preferred release path is a normal direct push to main when permitted. If rules require a PR, follow them and wait for merge; never bypass protection.
- The first publication depends on GOP-7's end-to-end validation. Verify completion through available issue/session evidence. If it is incomplete or unknown, explain the remaining checks and limit this run to preparation/validation; do not publish. Do not require a Linear connector if the user has already confirmed completion.

## 1. Agree on the version

Propose patch, minor, or major with the resulting version and a short explanation based on the actual changes. Validate the proposal with `scripts/bundle.py`'s `bundle_version` and require it to exceed all published stable releases.

For the first release, the existing valid Cargo version (for example, 0.1.0) may be proposed unchanged. Still ask for the user's explicit version choice; do not silently select it. Summarize the full product for first-release notes rather than pretending a previous release exists.

Wait for the answer before editing versions. Silence or elapsed time is not approval. After the choice, update only the root Gopher package version in Cargo.toml and Cargo.lock, without upgrading dependencies. Bundle versions are generated by packaging; do not manually bump Info.plist or duplicate version constants.

## 2. Agree on the changelog

Draft the exact `## [<version>] - YYYY-MM-DD` section and present it for notes or approval. Describe user-facing changes concisely; include material fixes and compatibility changes, not every commit or internal refactor. Do not invent changes from commit titles alone. Use the user's current date.

Wait for explicit approval before writing the section to CHANGELOG.md, committing, pushing, or dispatching. Incorporate requested edits and present revised text for approval unless the user explicitly approved those exact edits as final. Preserve older sections and unrelated Unreleased entries; remove only entries covered by the approved release. A release section must contain actual release notes, not placeholders.

In a request to publish a release, approval of this section authorizes the remaining release steps for the reviewed changes and chosen version; do not add another routine confirmation. A prepare-only or validate-only request does not authorize publication. If intervening changes materially alter the release scope, return to the affected approval step.

## 3. Validate, commit, and push

- Write the approved section and run the repository's Rust and Python checks from AGENTS.md. Call `release.metadata(root)` from `scripts/release.py` to validate the version/lock/changelog locally; do not fake GitHub Actions environment variables to bypass workflow guards.
- Review the final diff. Stage only the intended release files and commit with a Conventional Commit such as `chore(release): prepare v0.2.0`.
- Fetch main again before pushing. If it advanced since the reviewed base, inspect the additional commits, reassess the version/notes, and seek renewed approval when scope changes. Do not silently release the new commits, force-push, or automatically retry a rejected push. A normal explicit `git push origin HEAD:refs/heads/main` is the preferred path when permitted.
- For a required PR, preserve the approved preparation and wait for its merge. Verify the resulting main commit's complete release scope, since merges may include other work.
- Record the exact full SHA eligible for dispatch. Confirm it is current remote main, and check version/tag/draft eligibility using the existing release validation logic. A conflicting published version needs a new version choice; a draft for another commit needs the documented recovery procedure.

## 4. Dispatch and follow the specific run

The workflow must already exist on main. Use the approved full SHA as `expected_sha`, explicitly select the intended mode, and dispatch once:

```sh
gh workflow run release.yml --repo mbuvarp/gopher --ref main \
  -f mode=publish -f expected_sha="$release_sha"
```

Use `mode=validate` for validation-only work or while first-release checks remain incomplete. Publish mode already runs validation and packaging; a separate validation dispatch is not required for every release.

Record the dispatch time and use the returned run URL/ID when available. Otherwise locate the workflow_dispatch run by workflow, approved head SHA, actor, and creation time. If multiple runs match or the dispatch response is uncertain, inspect before taking further action; do not guess the latest run or dispatch again. Follow that exact run to completion and read failed-job logs as needed.

The workflow pins its checkout and rejects an unexpected SHA before signing or publication. If this guard fires, inspect the new main changes and reassess approvals before another dispatch. Never drop `expected_sha` to get past the failure.

On success, report the version, commit, workflow run, and release URL (or validation artifact URL). Confirm a published release is immutable and has the expected assets. On failure, report the failing stage and whether a draft/published release exists. Do not automatically retry publication or delete tags/releases. Matching unpublished drafts can be recovered on a user-requested retry using the existing workflow; published versions must never be overwritten.
